# 大创造时代网页版：Colyseus 实现方案与开发计划

> 版本：v1（2026-11-18）
> 技术基线：Colyseus 0.18（2026-08-20 发布，官方称为 1.0 前最后一个大版本）、`@colyseus/schema` 5.x、客户端 `@colyseus/sdk` 0.18.x
> 文中代码均为**示意**，具体 API 签名以 docs.colyseus.io 为准。

---

## 1. 目标与范围

**目标**：2–5 名朋友在浏览器里联机，完整打完一局《神秘大地：大创造时代》（Terra Mystica: Age of Innovation），非商业、私下使用。

**MVP 必须有**

- 用房间码（room code）开房 / 加入，选座位
- 完整规则：6 轮、全部 12 个派系（faction）、7 种家园地形（planning display）、宫殿板块、创新板块、能力板块、城市板块、书本行动、科学（science）四条学科
- 服务器校验每一步（防误操作、防作弊）
- 断线重连，刷新页面不丢局；服务器重启后能续局
- 游戏日志 + 终局计分明细

**MVP 不做（以后再说）**

- AI 机器人、单人 Automa 模式
- 天梯、排名、账号系统
- 手机端专门适配（先保证桌面浏览器）
- 跨天的异步对局（async play）推送通知

**两点前提**

1. Board Game Arena（BGA）上已有官方授权的 Age of Innovation。如果只是想玩，那里就能玩；这个项目的价值在于自己定制规则体验、练手。BGA 也是很好的**规则对照工具**：拿不准的规则细节可以去那里开一局验证。
2. 版权：规则机制可以自己实现，但官方美术、图标、版图扫描图不要公开发布。仓库设为私有，素材用自绘的简单几何图形或 CC 授权图标（如 game-icons.net，CC BY 3.0，需署名）。

## 2. 总体架构

### 2.1 三条核心原则

1. **规则引擎与网络层解耦**：规则写成一个纯 TypeScript 包（`packages/engine`），不依赖 Colyseus、不依赖浏览器。服务端用它校验和执行，客户端用同一份代码做"预览 / 高亮合法目标"。
2. **服务器权威**（authoritative server）：客户端只发"意图"（我想在 E7 建工坊），服务器判定合法后执行，再把结果下发。客户端永远不自己改正式状态。
3. **事件溯源**（event sourcing）：一局游戏 = 初始设置（setup）+ 随机种子（seed）+ 指令日志（move log）。任何时刻的状态都能由日志重放（replay）得到。存档、断线续局、撤销（undo）、复盘、bug 复现全部建立在这一点上。

## 3. 技术选型

| 层 | 选择 | 理由 |
|---|---|---|
| 语言 | TypeScript（全栈） | 引擎前后端共用；Colyseus 0.17 起支持全栈类型安全（客户端可 import 服务端类型） |
| 运行时 | Node.js 22 / 24 LTS | Colyseus 官方支持 |
| 联机框架 | Colyseus 0.18 | 房间、匹配（matchmaking）、自动重连、请求/响应消息、限流都现成 |
| 前端 | React + Vite | 生态成熟，组件化适合大量面板 |
| 地图渲染 | SVG | 六边形格子数量不多，SVG 点击、悬停、缩放、样式都简单；不需要 PixiJS/Canvas |
| 前端状态 | Zustand | 轻量，适合"整份快照替换 + 局部 UI 状态" |
| 消息校验 | Zod | 服务端对客户端载荷（payload）做结构校验 |
| 测试 | Vitest、`@colyseus/testing`、Playwright | 引擎单测 / 房间集成测试 / 多浏览器端到端测试 |
| 存储 | SQLite（better-sqlite3 或 Drizzle）；可选 `@colyseus/database` | 朋友局数据量极小，单文件数据库足够；0.18 新出的 `@colyseus/database` 自带带乐观锁的版本化存档，也可以考虑 |
| 部署 | 香港轻量云服务器 + Caddy（自动 HTTPS）+ pm2 或 Docker | 见第 8 节 |

**为什么不让 Colyseus Schema 承载完整游戏状态？** 见 5.2。

## 4. 规则引擎设计（最核心、工作量最大的部分）

### 4.1 引擎 API

```ts
// packages/engine/src/index.ts（示意）
createGame(setup: SetupOptions, seed: string): GameState
getLegalMoves(state: GameState, seat: Seat): MoveTemplate[] // 给前端高亮用
validateMove(state: GameState, seat: Seat, move: Move): RuleError | null
applyMove(state: GameState, seat: Seat, move: Move): { state: GameState; events: GameEvent[] }
replay(setup: SetupOptions, seed: string, log: LoggedMove[]): GameState
scoreBreakdown(state: GameState): ScoreSheet
```

约束：

- **纯函数**（pure function）：同样的输入永远得到同样的输出；不读时间、不用 `Math.random()`，随机全部走带种子的伪随机数生成器（seeded PRNG）。
- **不可变更新**（immutable update）：`applyMove` 返回新状态，旧状态不变。用 Immer 可以写得像直接修改一样简洁。
- `events` 是"发生了什么"的描述（例如 `{ type: "built", seat, hex, building }`、`{ type: "cityFounded", … }`），用于日志文字、动画和音效。

### 4.2 状态模型（GameState）

```ts
interface GameState {
  version: number;              // 每执行一条指令 +1，用于并发控制
  setup: SetupOptions;          // 人数、派系分配方式、是否用变体
  round: 0 | 1 | 2 | 3 | 4 | 5 | 6;  // 0 = 开局设置阶段
  phase: "setup" | "income" | "actions" | "scienceBonus" | "finalScoring" | "ended";
  turnOrder: Seat[];            // 本轮行动顺序
  nextTurnOrder: Seat[];        // 按 pass 先后形成的下轮顺序
  active: { seat: Seat; stage: TurnStage } | null;
  pending: Decision[];          // 待决策队列，见 4.4
  map: Record<HexId, HexState>; // 地形、建筑、归属、桥
  players: PlayerState[];       // 资源、能量碗、轨道、建筑库存、已得板块
  board: SharedBoard;           // 能量行动 / 书本行动占用、学科轨道、
                                // 创新展示区、能力板块区、宫殿板块、
                                // 回合奖励板块、城市板块、回合计分板块
  rng: RngState;
}

interface PlayerState {
  seat: Seat;
  faction: FactionId;
  homeland: TerrainType;        // 家园地形（由 planning display 决定）
  vp: number;
  coins: number; tools: number; scholars: number;
  books: Record<Discipline, number>;
  power: [number, number, number];   // 能量碗 I / II / III
  tracks: { terraforming: number; sailing: number };
  science: Record<Discipline, number>;   // 0–12
  keys: number;                 // 城市钥匙
  supply: Record<BuildingType, number>;  // 未建造的建筑
  tiles: { palace?: PalaceTileId; innovations: InnovationId[];
           competencies: CompetencyId[]; cities: CityTileId[];
           bonus?: BonusTileId };
  usedSpecialActions: string[];
  passed: boolean;
}
```

### 4.3 指令（Move）

```ts
type Move =
  // 开局
  | { t: "pickSet"; planning: PlanningId; faction: FactionId; bonus: BonusTileId }
  | { t: "placeInitialWorkshop"; hex: HexId }
  // 自由行动：自己回合内、主行动前后不限次数
  | { t: "convert"; conversion: ConversionId; times: number }
  | { t: "sacrificePower"; n: number }
  // 主行动：每回合一个
  | { t: "terraformAndBuild"; hex: HexId; build: boolean }
  | { t: "upgrade"; hex: HexId; to: "guild" | "school" | "palace" | "university" }
  | { t: "advanceTrack"; track: "terraforming" | "sailing" }
  | { t: "sendScholar"; discipline: Discipline; space?: number }
  | { t: "developInnovation"; tile: InnovationId; payment: BookPayment }
  | { t: "powerAction"; id: PowerActionId; args?: ActionArgs }
  | { t: "bookAction"; id: BookActionId; args?: ActionArgs }
  | { t: "specialAction"; source: string; args?: ActionArgs }
  | { t: "pass"; bonus?: BonusTileId }
  // 回合控制与决策
  | { t: "endTurn" }
  | { t: "decide"; decisionId: string; choice: unknown }; // 吸能、选城市板块、选能力板块……
```

### 4.4 回合状态机与"待决策队列"

整局流程：

```
setup（选组合 → 放初始工坊：正序一轮、逆序一轮）
  → 第 1–6 轮：[ I 收入 → II 行动（轮流，直到全部 pass）→ III 科学奖励与整理 ]
     （第 6 轮跳过 III）
  → 终局计分 → ended
```

**一个玩家的回合拆成几个子阶段**（`TurnStage`）：

1. `beforeAction`：可以做任意次资源转换
2. 执行主行动
3. 处理主行动引出的**后续决策**：组成城市 → 选城市板块；建学校 / 大学 → 选能力板块；获得铲子奖励 → 选地块……
4. `afterAction`：还可以再做转换
5. 玩家点"结束回合"（`endTurn`）才真正提交

**待决策队列**（pending decision queue）是这套规则里最容易写乱的地方，必须一开始就设计好：

```ts
interface Decision {
  id: string;
  seat: Seat;                 // 谁来决定（不一定是当前行动者）
  kind: "leech" | "chooseCityTile" | "chooseCompetency" | "useBonusSpades" | …;
  options: unknown;           // 可选项
  blocking: boolean;          // 是否必须先处理完才能继续
}
```

最典型的"回合外决策"是**吸能**（leech，邻居建造时获得能量）：

- 规则：别人建造 / 升级后，相邻的每个玩家可选择获得能量；获得 N 点能量要付 N−1 分，且一般不能只拿一部分（细则见规则书"Gaining Power from Builds"）。
- 设计：吸能机会在建造者**结束回合之后**才发给邻居。这样建造者在自己回合内撤销操作时，不会牵扯到别人已经做出的决定。
- v1 采用"阻塞"：吸能决策没回完，下一位玩家不能开始行动。配合"自动接受规则"减少等待（例如：代价为 0 时自动接受；玩家可设置"代价 ≤ N 分自动接受"）。
- 以后可以改成 Snellman 在线 Terra Mystica 那种非阻塞的异步吸能。

### 4.5 内容数据化 + 效果钩子

需要编码的内容清单（数量来自官方规则书组件表）：

| 内容 | 数量 | 实现方式 |
|---|---|---|
| 派系（faction） | 12 | 数据表 + 钩子（被动能力、特殊行动、宫殿效果差异） |
| 家园 / 规划板（planning display） | 7（双层） | 数据表：家园地形、收入图标、建筑覆盖格 |
| 宫殿板块（palace tile） | 17 | 数据表 + 钩子 |
| 创新板块（innovation） | 18（3 种特殊能力 + 9 种即时收益 + 6 种额外建筑） | 数据表 + 钩子 |
| 能力板块（competency） | 12 种 × 4 张 | 数据表 + 钩子 |
| 城市板块（city tile） | 7 种 × 3 张 | 数据表（分数 + 一次性奖励 + 钥匙） |
| 回合计分板块（round score） | 12 + 4 张终局回合板块 | 数据表：行动得分条件 + 科学奖励 |
| 回合奖励板块（round bonus） | 10 | 数据表 |
| 书本行动（book action） | 6 | 数据表 + 钩子 |
| 能量行动（power action） | 6（固定） | 数据表 |

合计约 **90 多个内容项**。其中大部分只是"获得 X 资源 / 某事件触发时得 Y 分"，可以用声明式数据描述；少数真正改变规则的（改变邻接判定、改变费用、额外行动）才写代码钩子：

```ts
// 声明式：大多数板块
{ id: "bonus-03", income: { coins: 2 }, onPass: { perBuilding: { workshop: { vp: 1 } } } }

// 钩子式：少数特殊能力
{
  id: "innovation-xx",
  hooks: {
    modifyCost(ctx, action, cost) { /* 返回调整后的费用 */ },
    onEvent(ctx, ev) { if (ev.type === "built" && ev.seat === ctx.owner) ctx.gain(ctx.owner, { vp: 2 }) },
  },
}
```

引擎内部用一个事件总线（event bus）：每条指令执行时产生事件，依次分发给该玩家持有的所有派系 / 板块钩子。这样新增一个板块只需加一条数据，而不用改主流程。

### 4.6 地图与邻接

- 坐标：六边形轴向坐标（axial coordinates，q/r），同时保留版图上的格子编号（如 "E7"）方便日志显示。
- 地图数据：版图按人数有不同面，需要把每个格子的地形、河流手工录入成 JSON。建议先花半天做 `tools/map-editor`：网页上点格子选地形，一键导出 JSON，比手写不容易出错。
- 需要的图算法（全部写成纯函数并单测）：
  - **直接相邻**（direct adjacency）：共享边的格子，过桥也算
  - **间接相邻 / 可达**（reach）：隔河、在航行（sailing）距离内
  - **城市判定**：相连建筑组的数量与能量值之和（网上摘要的说法是一般 4 座、能量合计 ≥ 7，含大学或纪念碑时所需座数更少；具体数字以规则书为准）
  - **终局区域计分**：最大连通区域（按可达范围），用 BFS / 并查集（union-find）
- 具体哪些计算用"直接相邻"、哪些用"可达"，写代码前对照规则书逐条确认。

### 4.7 撤销（undo）

- **自己回合内**、还没点"结束回合"：随时撤销，实现方式就是从日志重放到本回合开始。
- **已经提交的回合**：发起撤销请求，所有玩家同意才回退（因为别人可能已经基于这个结果做了决定）。
- 有了事件溯源，这两种撤销都只是"截断日志 + 重放"。

## 5. Colyseus 服务端设计

### 5.1 房间划分

- `GameRoom`：一局游戏一个房间。房主创建时生成 6 位房间码，朋友用房间码加入（`joinById` 或按 `code` 过滤匹配）。
- 大厅（可选）：Colyseus 内置 `LobbyRoom` 可以列出进行中的房间；朋友局用房间码就够了，可以先不做。
- 用 0.17 引入的 `defineServer()` / `defineRoom()` 注册房间，客户端 `new Client<typeof server>(url)` 获得完整类型提示。

### 5.2 状态同步策略（关键取舍）

Colyseus 的招牌功能是 Schema 增量同步：服务器改状态，框架自动把差异（delta patch）推给客户端。但对这个项目，推荐**混合方案**：

- **Schema（`RoomMeta`）只放房间元数据**：座位列表（昵称、是否在线、座位号、派系名）、当前阶段、当前需要行动 / 决策的座位、`version`。这些字段少、变化频繁，适合自动同步，前端用 `onChange` 回调就能实时显示"谁在线 / 轮到谁"。
- **完整游戏状态以 JSON 快照下发**：每执行一条指令，服务器广播 `snapshot`（`version` + 公开游戏状态 + 本步 `events`）。玩家加入或重连时单独发一次。

理由：

1. **单一数据源**：游戏状态只在引擎里定义一次。若全部镜像进 Schema，就要维护"引擎类型 + Schema 类 + 双向映射"三套东西，每加一个规则字段改三处。
2. **回合制，数据量小**：一份完整状态大概几十 KB，几秒到几分钟才变一次，带宽完全不是问题。
3. **信息几乎全公开**：这个游戏基本是公开信息博弈，不需要用 StateView 做每个玩家不同的视图。少数需要隐藏的（例如双人局里背面朝上、第 6 轮才翻开的区域计分板块），由服务端在生成公开快照时剔除即可。
4. **Schema 有约束**：0.18 起每个 Schema 最多 63 个字段，嵌套数组等结构也受限，硬套复杂规则状态很别扭。

如果后面想练习 Schema 同步，或者想要更细粒度的动画，可以再把地图格子、玩家资源迁移到 Schema（只同步、不参与规则计算）。

### 5.3 消息协议

| 方向 | 消息 | 内容 | 说明 |
|---|---|---|---|
| C→S | `move` | `{ move, version }` | 用 0.18 的 `room.request` 请求/响应模式，服务器返回成功或带原因的拒绝 |
| C→S | `undo:request` / `undo:vote` | 目标版本 / 同意与否 | 跨回合撤销投票 |
| C→S | `pref:set` | 自动吸能阈值等 | 玩家偏好 |
| C→S | `chat` | 文本 | 可选 |
| S→C | `snapshot` | `{ version, state, events }` | 每步广播；加入/重连时单发 |
| S→C | `undo:proposal` | 发起人、目标版本 | |
| S→C | （Schema 自动同步） | `RoomMeta` | 座位、在线状态、当前行动者 |

### 5.4 指令处理流程

```ts
// apps/backend/src/rooms/GameRoom.ts（示意，以官方文档为准）
export class GameRoom extends Room<{ state: RoomMeta }> {
  private game!: GameState;

  messages = {
    move: (client, payload, ctx) => {
      const parsed = MovePayload.safeParse(payload);          // ① Zod 结构校验
      if (!parsed.success) return ctx.reject("bad-payload");

      const seat = this.seatOf(client);                       // ② 身份
      if (seat === undefined) return ctx.reject("not-seated");

      if (parsed.data.version !== this.game.version)          // ③ 乐观并发控制：
        return ctx.reject("stale-version");                   //    防双击、防基于旧状态的操作

      const err = validateMove(this.game, seat, parsed.data.move); // ④ 规则校验
      if (err) return ctx.reject(err.code);

      const { state, events } = applyMove(this.game, seat, parsed.data.move);
      this.store.appendMove(this.gameId, state.version, seat, parsed.data.move); // ⑤ 先落盘
      this.game = state;
      this.syncMeta();                                         // ⑥ 更新 RoomMeta
      this.broadcast("snapshot", { version: state.version, state: toPublic(state), events });
      return { ok: true, version: state.version };            // ⑦ 回应请求方
    },
  };
}
```

客户端：

```ts
try {
  await room.request("move", { move, version: store.version });
} catch (e) {
  toast(ruleErrorText(e)); // 例如 "铲子不够" "这里不和你的建筑相邻"
}
```

### 5.5 身份、座位与重连

- 不做账号系统：玩家输入昵称；入座时服务器发一个随机 `seatToken`，前端存 `localStorage`。
- **短时断线**：0.17 起 SDK 自动重连；服务端在 `onDrop` 里标记离线并 `allowReconnection(client, 秒数)`，`onReconnect` 里恢复在线并补发快照。
- **长时间离开 / 换设备**：凭房间码 + `seatToken` 重新加入，`onAuth` 校验后接管原座位。
- 座位不会因为离线被删除；游戏只是等这个人回来。
- 不要开 `IdleKickPlugin`：桌游玩家想很久是正常的。

### 5.6 持久化

```sql
games(id, code, setup_json, seed, engine_version, status, created_at, updated_at)
moves(game_id, seq, seat, move_json, created_at)   -- 主键 (game_id, seq)
```

- 每条合法指令**先写库再广播**；写库失败就拒绝这步。
- 房间在所有人离开后自动销毁（autoDispose），但局面在库里。下次有人用房间码进来：创建房间 → 读出 setup + moves → `replay()` 恢复。
- 存 `engine_version`：以后改了规则代码，旧存档能识别出来（必要时提示"此存档由旧版本创建"）。
- 完整日志还能导出成 JSON，用作测试用例（见第 7 节）。

### 5.7 安全

- 所有载荷 Zod 校验；服务器绝不信任客户端算的任何数值。
- 开启 `maxMessagesPerSecond` 限流（0.17 新增）。
- 房间码足够随机，避免陌生人误入；可选房间密码。

```
├───────────────┬───────────────────────────┬───────────────┤
│ 日志 / 聊天   │        地图（SVG）         │ 我的玩家板    │
│               │                           │ 资源 · 能量碗 │
│               │                           │ 轨道 · 板块   │
│               ├───────────────────────────┤ 其他玩家摘要  │
│               │ 公共区：能量/书本行动、    │               │
│               │ 学科轨道、创新/能力展示区  │               │
├───────────────┴───────────────────────────┴───────────────┤
│ 行动栏：主行动按钮 · 转换 · 待决策提示 · 结束回合 · 撤销   │
└───────────────────────────────────────────────────────────┘
```

### 6.2 交互模式："意图构建器"（intent builder）

1. 点"改造并建造" → 前端本地调用 `getLegalMoves(state, mySeat)`，地图上高亮所有合法格子，悬停显示费用（铲子、工具、金币）。
2. 点格子 → 弹出确认（例如"需要 2 铲 = 6 工具，确认？"）。
3. 确认 → `room.request("move")`；成功后等快照刷新，失败弹出原因。
4. 因为前后端是同一份引擎，前端高亮的就是服务器会接受的，基本不会出现"点了却被拒"。

### 6.3 其他

- 轮到自己：标签页标题闪烁 + 提示音（朋友通常边语音边玩，切走窗口很常见）。
- 终局：计分明细表（区域、学科、资源换分、回合板块得分逐轮列出）。
- 文案中文为主，规则术语保留英文对照（如 能力板块 / Competency）。
- 素材：派系用颜色 + 文字标签，建筑用简单几何形状（工坊 = 小方块，行会 = 房子形，宫殿 = 大方块……），完全不依赖官方美术。

## 7. 测试策略

规则引擎是全项目风险最高的部分，测试投入要大于界面。

| 层级 | 内容 | 工具 |
|---|---|---|
| 单元测试（unit test） | 每条规则一组用例：费用计算、邻接、城市判定、吸能代价、科学轨道钥匙限制…… | Vitest |
| 内容测试 | 每个派系 / 板块至少一个用例，验证效果与触发时机 | Vitest |
| 整局回放测试（golden test） | 把真实对局（线下实体局记录，或在 BGA 上打的一局）录成指令日志，断言终局各家分数和关键中间状态 | Vitest + 日志 JSON |
| 随机对局模糊测试（fuzzing） | 机器人每步从 `getLegalMoves` 随机选，跑上千局，检查不变量 | Vitest |
| 房间集成测试 | 多客户端加入、轮流行动、非法指令被拒、断线重连、服务器重启后续局 | `@colyseus/testing` |
| 端到端测试（E2E） | 3 个浏览器窗口完整打几个回合 | Playwright |

**不变量**（invariant），每步之后自动检查：

- 能量指示物守恒：三个碗的总数只会因牺牲能量、或明确增减指示物的效果而变化
- 任何资源不为负
- 建筑库存 + 版图上的建筑 = 初始数量（工坊 9、行会 4、宫殿 1、学校 3、大学 1；创新板块带来的额外建筑单独计）
- 每个学科第 12 格最多一人
- 游戏一定会结束（不会卡在没有合法指令的状态）

随机机器人还有一个好处：开发期一个人就能凑满 5 人局测试。

## 8. 部署

- **服务器位置**：朋友大多在国内的话，推荐**香港**的轻量云服务器（1 核 2G 足够）。大陆服务器用域名对外提供网站需要 ICP 备案；回合制游戏对延迟不敏感，香港延迟完全够用。
- **HTTPS / WSS**：Caddy 反向代理，自动申请证书，WebSocket 无需额外配置：

  ```
  aoi.你的域名.com {
      reverse_proxy localhost:2567
  }
  ```

- **进程**：单进程即可（朋友局不需要多进程 / Redis）；pm2 守护，或 Docker Compose。
- **前端**：`vite build` 出的静态文件由 Caddy 直接提供，或由 Colyseus 内置的 Express 托管。
- **备份**：每天定时复制 SQLite 文件。
- **早期内测**：先在本机起服务，用局域网或内网穿透给一两位朋友试玩，再上云。

## 10. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 规则理解偏差 | 算错分、朋友不信任结果 | 以官方规则书为准逐条核对；有疑问去 BGA 实测；用真实对局做回放测试 |
| 网上规则摘要不可靠 | 数据表录错 | 只从官方规则书录入。例：两份网上摘要对"剩余金币换分"的比例说法就不一致（3:1 和 5:1），这种必须查原书 |
| 待决策 / 吸能逻辑写乱 | 卡局、状态不一致 | 4.4 的决策队列一开始就设计；不变量 + 随机对局测试 |
| 特殊能力数量多 | 工期拉长 | 数据化 + 钩子；M1 先做无能力基础版，M3 按派系逐个加 |
| 地图录入错误 | 邻接判断错 | 做地图编辑器；录入后叠在版图照片上目视核对（照片仅本地使用） |
| 范围膨胀 | 迟迟打不上第一局 | 严格按里程碑；M2 结束就先和朋友玩基础版 |
| 规则改版导致旧存档不兼容 | 续局出错 | 存 `engine_version`；改动规则时保留旧存档回放测试 |
| 版权 | 法律风险 | 仓库私有、不公开部署官方素材、仅朋友使用 |
